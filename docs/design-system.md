### トップ(町)の扱い(v2.1)

- **町の場面**とは、トップの中で町の立体(と、その止めた画像)が描かれている場面の種類をいう。いまは最初の画面・その下のスクロールの舞台(病院の中と、病院を出た交差の広場の見晴らし=閉じ。v7)・建物をひらいたパネル・動かないときに舞台を置き換える区画(`.rmin` と閉じの区画)。同じカメラのまま続く次の場面も、町の立体を描くなら町の場面に入る。範囲は種類で決め、場面の中身・数・長さでは決めない(いまの値は §1 Motion の v7 の実測)。
- **町に限る。** 町の色・書体・部品・動きを、下層・紹介 LP・Compass・Products へ持ち出さない。下層とつなぐのは行き先・語・ロゴで、見た目は寄せない(`proto/top-ad/hiraku3/ia/README.md` d)。町の但し書きは町に限るので、町の部品を共通へ上げるには、§6 の前に憲法の改定が要る。

- **実体。** 町の CSS はトップの `<style>`、トークンはその `:root` と `html[data-tod]`、立体の色は描画コードの一か所(`town/buildings.js` の `PALETTE` と `town/world.js` の `TOD`)。JS と画像は `town/`(入口は `town/hiraku.js`。検査用の引数と撮り方は `town/tools/README.md`)。トップは `shared/bridge.js` を読み(計測・利用ログ・BudouX)、`shared/bridge.css` は読まない。ヘッダー・メニュー・フッターの語・行き先・列は、`bridge.js` の口(`window.BRIDGE` の `NAV`・`CTA`・`FOOTER`・`PRIVACY`。PR #172)から町の CSS で描く(`town/hiraku.js` の `drawChrome`。JS なし用に同じ中身を `index.html` に書き、`scripts/check-site.mjs` の6項が `bridge.js` と照合する。ia 提案 c・f)。bridge.css を読まないのは、町のトークンと二重にしないため、また町の札(`.tchip` `.ttag` `.otag`)と bridge.css の `.chip` `.tag` の役割が違うため(v2.3 で名を分けた。§6 町の部品の判断)。

### Motion

動きは構図・主役・現在地の変化を伝えるために使う。派手にするためには使わない。

- 登場は `[data-reveal]`(.6s・12px・`data-reveal-delay` 1〜4。観測は画面に入る前 `rootMargin 10%`・`threshold 0` で始まり、読む位置では不透明。2026-10-11 に 1s・24px・threshold .12 から縮めた: 本文の遅いフェードインにしない=社長指示)。段の単位に付け、本文の段落・リスト・CTA・見出しには付けない。hover は浮上 2〜4px・縁の色・矢印(.2〜.35s)。緩急は `--ease` の1本。
- `prefers-reduced-motion` では完成した姿を最初から見せる(共通 CSS で処理済み。ページ独自の動きも同じ扱い)。JS なしで中身が透明のまま残らないこと。
- 下層ヒーロー(`.page-hero`)の動きは、読み込み時に一度、見出しの下の線を左から引くだけ(`transform:scaleX` 約1秒)。砂の点は線が通った後に opacity だけで出る。既定値は完成形で、keyframes の from 側だけで動かす。ヒーローのパンくず・見出し・リードに `[data-reveal]` を付けない(見出しは最初からある)。ループ・スクロール連動・章ごとの線描きはしない(2026-10-04)。
- 常時ループは置かない(2026-10-11。トップのヒーローの Experience Journey を外した)。町の場面の生きている町だけは、下の「町の場面の動き」による。
- スクロールに従う動きは、トップの町の場面だけ(下の「町の場面の動き」)。筆の線のトップの開いた瞬間(`.hz`)・ページの線(`.pl`)・#about の閉じ(`.kz`)は、町を移した便で外した(改定履歴 v2.3)。

#### 町の場面の動き(v2.1)

出典は、社長の決裁(2026-10-28。v6 を採る。BRIEF 14.3 は、採ることを「町の場面に限って舞台の固定・スクロールで動くカメラ・物が見えてから出る札を認めること」とする)と、憲法 v1.10 の町の但し書き。範囲は町の場面(§0)という種類で決める。どの物へ寄るか、何画面か、では決めない。

- **生きている町** — 人・乗り物・雲・建物の小さな動きは常に動いてよい(上の「常時ループは置かない」の、町の場面だけの例外)。5秒を超えるので、町が画面に見えている間は止めるボタン(`aria-pressed="true"`=止めている)を置き、誘いの輪も一緒に止める(WCAG 2.2.2)。画面外・非表示のタブでは描かない。操作していないときは描く回数を落とす。時刻の切り替えは 1.2 秒でなめらかに。
- **ふれる → ひらく** — 押した手応えは 100ms 以内。寄る・ひらく・閉じるはばね(線形の補間を使わない)。道具へ移る瞬間は町の中の画面が広がる短い動きで、移動は待たせない。動きを減らす設定では瞬時。
- **スクロールの舞台** — 町を画面に固定(sticky)したまま、その下の舞台の進みでカメラを動かしてよい(上の項の「固定・吸着・スクロール量の書き換えをしない」のうち固定の、町の場面だけの例外)。進みの目標はスクロール位置だけで決まり、表示の進み(絵と、それに結びついた札・言葉・階の印・出口・押せる範囲。止めた画像でたどるときも同じ)は、それを区間ごとに決めた上限の速さで追う。速くはじいても、寄る・壁が倒れる・各階・引き上げを短い時間で見せてから追いつき、上限より遅いスクロールでは差を出さない。スクロールは止めない・吸着しない(2026-10-30 社長 案A)。舞台が画面の外にあるときと、最初の画面へ一気に戻ったときは、表示の進みをすぐ合わせる。吸着・ホイールの横取り・`touchmove` の `preventDefault`・スクロール量の書き換えをしない(例外は下の保証の 2 だけ)。止まっているあいだは描かない。絵は帯が畳まれたときの高さ(lvh)で描き、言葉と入口は帯が出ているときの高さ(svh)の中に置く。アドレスバーの開閉で進みも構図も跳ばない。
- **寄る途中で溶かす・消す** — カメラが主役へ寄る間、主役の手前と脇の物を、その時刻の空気の色へ溶かす、または短い区間で点描で消してよい。消すのは BRIDGE が描いた立体だけ。写し(建物の中の実画面)は消さず、加工しない(第22条 写しの但し書き)。
- **物が見えてから出るもの** — 認めるのは v6 にあるものと、v7 の閉じにあるものだけ。v6: 道具の札・「病院の中」の見出しと一文(階ごとの居場所と道具の一行を含む)・下の文字リンク。v7 の閉じ: 「病院の外」の見出しと本人の言葉(名乗りを含む)・明朝の一文・島の上の3つの札と現在地の点・道の先と文字リンクと第29条の一文(designer 2026-10-28。下の5つの条件をすべて満たすことを、動きを減らす設定・止めた画像・JS なしの撮影で確かめた)。それが指す物や場面が画面に見えてから出してよい。出したものは、その物や場面が画面にある間は出たまま残す(進みを戻したときは戻ってよい)。ただし、病院を出る戻し(溶かす・消した物を逆に戻す動き)が始まったら、病院の中の札・言葉・入口・階の印は、戻しと一緒に消してよい——戻しの始まりで「病院の中」の場面は終わり、札が指す部屋も戻しで閉じていくため。戻しより前に消さない(札のない開いた病院を見せない)。これより先の場面を足すときは、作ってから同じ5つの条件で判断する(先に認めない)。
- **2026-10-11 の社長指示「演出に内容の可視性を依存させない」(v1.7)との関係** — 物が見えてから出るものは、字面ではこの指示から外れる。外れを認めたのは社長の決裁(2026-10-28)で、町の場面に限る。指示の趣旨(中身に届かない人を作らない)は、次の5つで守る。1つでも欠けたものは出さない。
  1. 出る前のものは透明にするだけで、読み上げの順にいつもある(`display:none`・`visibility:hidden` にしない。見えない間は押せないだけ)
  2. キーボード: Tab で来たら、それが見える所まで舞台を進める(スクロール量の書き換えはこれだけ。フォーカスに応じるときだけで、動きを減らす設定では瞬時)。そのときは表示の進みの上限を外す(フォーカスした物が見えないまま待たせない)
  3. 動きを減らす設定: 舞台を畳み(固定・寄せ・溶かしをしない)、着いた所と同じ視点の止めた画像の区画に、札・言葉・出口を最初から出す
  4. WebGL なし・低性能の端末・描く器を失ったとき: 止めた画像で同じ進みをたどり、札・言葉・出口も同じ進みで出す
  5. JS なし: 舞台を作らない(止まった長い面を作らない)。建物の押せる範囲のリンクと `<noscript>` の一覧で、町が見せる行き先すべて(いまは道具の29件・考え方・運営者)に届く
- 町の場面の外(下層と、トップの町の場面でない区間)には、上の各項(固定しない・演出に可視性を依存させない・常時ループなし)がそのまま及ぶ。
- **v7 の実測(規定ではなく、いまの値)** — 舞台は最初の画面の下 約2.22画面(`--span:222.25svh`。v6 の 1.5画面に、閉じの約1画面を足した。393×724 でページの全長 3,012px)。病院の中までは v6 と同じ(進み p は v6 の単位=1.5画面で 1): 寄る .036–.43・壁が倒れる .25–.37・沈む .36–.42・外枠と階の印 .38–.43・「病院の中」と一文 .45–.49・3F .565 / 2F .70 / 1F .835・下の文字リンク .84–.88(1F までは v6 と画素の差 0)。閉じは 1F の .835 から s 画面で: 病院の中の札・言葉・階の印・下の文字リンクが消える +.15–.20(戻しと一緒)・カメラが引いて上がる +.15–.55・島の下のもやと下の端の地 +.49–.57・「病院の外」と本人の言葉 +.57–.61・明朝の一文 +.68–.72・島の上の札と現在地の点と灯る道 +.83–.86・道の先と文字リンクと第29条の一文 +.88–.92・舞台の終わり +.97。何も変わらない区間の最長 0.11画面(+.72–.83)。表示の進みの上限(1画面を通る最短の秒。`town/pace.js` の `PACE`): 寄り始め p 0– 1.0・壁が倒れて着くまで .25– 1.8・着いて「病院の中」.43– 1.2・各階と 1F .55– 1.8・引き上げ +.15– 1.5・閉じの言葉と出口 +.55– 1.0(最速で通しても 1F まで約1.9秒・舞台ぜんたい約3.1秒(平均 1画面 約1.4秒)。ばねの遅れで約0.3秒増える。各階は約0.36秒ずつ見える)。地の色の隣どうしの ΔE2000 の最大は夜 7.44・昼 1.34。帯が出ているときの高さ 560px 以下では、道の先・文字リンク・第29条の一文を舞台に重ねず、舞台のあとのふつうの流れに置く(島の大きさを残すため)。値を変えたら designer が見て、ここを書き換える。細部は `town/live.js` の `SQ`・`CL` と `town/hiraku.js` の `CL`。

## 4. Patterns

- **Page opening** — 下層は `.page-hero` 一つ(パンくず → h1(下を線が通り、書き出しの真下に砂の点) → リード1〜2文)。Products だけ、リードの下に「探す」(検索窓・用途のチップ・件数の aria-live)を置く(v1.7)。町の最初の画面(一行・見出し・島・Compass の入口と条件の一行・時刻と止めるボタン。PC は島が右の約3分の2)は、他ページへ複製しない。下層のヒーローに町の絵・部品を持ち出さない(v2.1)。 リードの下に置けるのは、そのページの最初の一歩を1つまで(`.toc` / 連絡先の一覧 / `.tx-link` / Products の探す)。Philosophy だけ、その前に核の一文 `.stmt`(筆の線のトップの `.idea-h` と同じ大きさと色だった。値は philosophy の側にある)を置く。ヒーローに Pill とボタンを足さない(v1.8)。

## 5. 共通の品質基準とプロダクトのデザイン

### プロダクトのデザイン

- **独立** — 思想は共有し、デザインは独立する(第30条の2)。プロダクトの画面は、色・書体・レイアウト・動き・部品・世界観を、目的と利用者と利用環境から選ぶ。`shared/bridge.css` を読むか、ブランドの値を使うかもプロダクトが決める。例外の承認は要らない。社長の言葉では「経営管理ツールは高度なSaaSらしくてもいい。学習アプリはポップでもいい。ゲームは没入感があってもいい。個人の実験的なプロジェクトでは全く異なるデザインを採用してもいい」。
- **決めごとの置き場** — そのプロダクトのディレクトリ(README と styles.css の `:root`。大きなものは docs/。例: `clinic-flow-3d/docs/ux-audit-v85.md` §4)。プロダクトの中では、そのプロダクトのトークン・部品を先に使う。足すのに §6 の可は要らない。他のプロダクトの styles.css を、理由なく雛形として写さない(選ぶなら前提の5行目に合う理由を書く)。
- **前提(新規と、方向を作り直すとき)** — 作る前に README に5行まで書く。方向を作り直すとは、そのプロダクトの色・書体・レイアウトの系(`:root` のトークンの体系)を入れ替えることをいう。画面や部品を足すこと、既存の系の中で直すことは含まない(designer のモード B)。比べ方は文章を既定にし、product-idea の提案の中で行う(dev-loop)。見た目の差が言葉で伝わらないときだけ、いちばん使う1画面のモックを添える。designer が推奨を1つ出し、決めるのはふだんの product-idea の判断である。別の承認の段は置かない。前提が書かれないまま作られていても、出荷は止めず、README に書き足す。
  1. 誰が・何を(第31条の申告を指せば足りる)
  2. どこで(端末・場面)
  3. どんな体験(感情と操作)
  4. 比べた方向(2〜3案の名前。1つは既存と違う出発点から)
  5. 選んだ方向と理由(ブランドの見た目を選ぶときも、合う理由を書く)
- **既存のプロダクト** — 公開中の見た目は、そのプロダクトの選択として引き継ぐ(第30条の2第2号)。2026-07 のリカラーでブランドの値を写したものも、独自のものも同じ。一括で作り直さず、リカラー前の色へ戻す義務もない。前提を後から書く必要もない(書くのは方向を作り直すときだけ)。ブランドの規定に合わせるための課題は、プロダクトの課題としては閉じる。
- **ブランドとの接点** — BRIDGE の名・マーク・公式サイトへの道を、置くか、どこに置くかはプロダクトが設計する(第30条の2第5号)。マークを置くときは第24条の2(静かに置く・意味を固定しない)に従い、正式ロゴの経路を変えない(写しの散らばりは B-22・未決事項#7)。紹介ページは、公式サイトの一部として作るならブランドの面(§0・§4。subpage.css)、プロダクトの見た目で作るならプロダクトの画面である。
- **clinic-flow-3d** — この原則の初例(2026-09-12)。基準は `clinic-flow-3d/docs/ux-audit-v85.md` §4(板とパネル・意味色・線画 SVG のアイコン)。ゲーム類型の文体・文字量・三分法・正式名称は context.md 冒頭の棲み分けのまま。

## 6. 増やすときの規則

ブランドの面の新しい Component / token / pattern は、次を**すべて満たすときだけ**足す。判断は designer。プロダクトの部品・トークンはここを通らない(§5)。

1. 既存の部品(§3)・型(§4)では表せない
2. 使う場所の2か所目が実際に現れている
3. 交差・余白・選択の瞬間で説明できる
4. ひとり運営の保守に見合う

- 一度しか使わないものは、そのページの `<style>` に置く。共通へ昇格させない(第14条の UI 版)。
- 同じ UI が3か所以上で独自に実装されていたら共通化を検討する。見た目を変えずに1か所ずつ。数えるのはブランドの面の中だけで、プロダクトどうしの値が同じでも共通化の理由にしない。
- 品質の直し(44px など)は面をまたいで行ってよい。見た目の値の追従は求めない(プロダクトが自分の理由で揃えるのは、そのプロダクトの選択)。`bridge.css` の値を変えたときにプロダクトへ写す作業はせず、プロダクトの値もブランドの面へ写さない。
- トークンは役割の名前で足す(色名にしない)。色数が増えないかを第22条で照合する。
- 使われなくなった部品・トークンは、全ディレクトリで未使用を確かめてから消す。
- 憲法に触れる判断は designer が決めない。PM・auditor 経由で社長へ(第33条)。
- UI 変更の流れは CLAUDE.md のとおり(憲法 → 本書 → その面の既存の部品・トークン確認 → designer → 実装 → qa → pm → 社長)。
