## 2. 情報設計(IA)の原則

1. **Homeは玄関、長い説明はしない(Home = 町で出会う、Products = 一覧で選ぶ)** — Homeの役割は「誰に・何が役立つか」の一言と、次に触るもの(試しているもの)を渡すこと。理念の全文はPhilosophyに、用途別の索引はProductsに置く。(v2.1: 「説明はしない」から改定。初めて訪れた医療職が最初の画面で用途を理解できることを優先する / v2.2: 常時表示の文字量を半分以下にし、見て分かる構成に。用途別索引をHomeから外す / v2.6: 商品の一覧に見せない。Home=気になるものを触る、Products=全部探す / v2.8: 最初の画面の主役は BRIDGE と動き。誰に何が役立つかの一文は動きのすぐ下の帯に置く(PC は最初の画面に入る。スマホは CTA のすぐ下で最初の画面の外になり、最初の画面で用途を伝える役は、動きの語〈退院支援→合意形成〉と CTA の添え書き〈10の質問・約3分・登録不要〉が担う) / v2.9: スマホも説明の一文と CTA を最初の画面に入れる(動きの語は外した) / v3.1: 用途6つの帯「目的から探す」を Home に置く。v2.2 で外した索引そのものではなく、Products の各節へ渡すだけの薄い帯(社長指示 2026-10-11「用途別の入口」) / v3.4: Home を町に。用途6つは町の6棟になり、各棟のパネルの末尾「この用途を一覧で比べる(n点)」が Products の `#用途` へ渡す。Products から町へはロゴとパンくずの Home)
2. **1ページ=1つの問い** — Home「どこから歩く?」/ Philosophy「なぜ?」/ Projects「いま何を?」/ Products「何が使える?」/ Stories「何が変わる?」/ Journal「途中はどうなってる?」/ Research「確かめたのか?」/ About「誰が?」/ Community「どう関わる?」(入口の名は NAV の CTA と同じ「話をする」。連絡先を先に、4つの関わり方は下に。v3.2)
3. **深さは3階層まで** — Home → セクションページ → 個別ページ。それ以上掘らせない。
4. **どのページからでも次へ歩ける** — 全ページ末尾に「Where to next(次はどこへ歩きますか)」の3分岐。行き止まりを作らない。
5. **押し付けない** — CTAは常に複数(読む/話す/使う/作る)。「何もしなくても十分」を明文化(明文化は行動を求めるページで。v3.2)。

## 3. ナビゲーション設計

### デスクトップ(>920px)
- 固定ヘッダー(スクロールで背景ブラー+ボーダー)
- 左:ロゴ(→Home) / 右:Products · Philosophy · Journal · About(テキストリンク、現在地はアンダーライン)+ Contact(ボタン)+ テーマ切替。Projects · Stories · Services はドロワーとフッターから(v2.1: 個人がプロダクトを試す導線を法人向け相談より前に置く)
- Home(町。v3.4): `.site-nav` を置かず、同じ語(NAV.en)・同じ順・同じ行き先を町の CSS で描く(`bridge.js` の `window.BRIDGE`)。町が画面にある間は時刻と止めるボタン。舞台を抜けたら小さな帯に固定(地はフッターと同じ)。ロゴはしまわない。スマホの最初の画面に一覧への文字リンクは置かない(メニューの Products とパネルの「一覧で比べる」で足りる)
- Mega Menuは現段階では不採用(ページ数8ではフラットの方が認知負荷が低い)。ページが15を超えたら「思想/活動/道具/つながる」の4グループでMega Menu化する。

### モバイル(≤920px)
- ロゴ+ハンバーガー+テーマ切替のみ
- ハンバーガー → フルスクリーン「探索の地図」:全ページ+各1行の説明を縦に列挙(順に立ち上がるアニメーション)。説明付きにすることで、メニュー自体が「選べる地図」になる。

### フッター
- 全ページ共通のサイトマップ(思想/活動/つくったもの/つながる の4列)。ページの最後に、もう一度地図を渡す。

## 8. モバイルUX

- ハンバーガー→フルスクリーン地図(説明付きリンク)。タップ領域は44px以上。
- 一覧はすべて1カラムに畳む。行リストは番号を隠し要点のみ。
- 固定ヘッダーは12px+blurで薄く。Philosophy と Stories はヒーローに静的な目次(`.toc`)を置く(sticky にしない。v3.2)。
- アニメーションは`prefers-reduced-motion`で全停止。
- 段の登場(`[data-reveal]`)は .6s・12px で、画面に入る前に始まり読む位置では不透明(2026-10-11)。本文の段落・リスト・CTA には付けない。

## 9. デスクトップUX

- フラットな7リンク+CTAボタン。現在地アンダーライン。
- ホバーで下線が左から伸びる/カードが浮く——「進める」ことを触覚的に示す。
- 本文の最大幅は660px(可読行長)。ステートメントは明朝・最大1180px。
- ライト/ダークは同一トークン(`--bg`等)の差し替えのみで完全対応。

## 10. 拡張性(100件以上に耐える設計)

- **プロダクト** … `products/index.html`の`PRODUCTS`配列に1オブジェクト追加するだけ(`use`=用途・`t`=日本語の機能名・`for`=誰向け・`kind`=行き先の種類(app/intro/dist)・`cta`=ボタン文言・`status`=例外の状態(paused)・`facts`=確認済みの利用条件)。用途は`USES`配列(`t`=語・`s`=チップの短い語・`p`=一文)で管理し、用途ごとのセクションと行・チップは自動生成。トップ(町)の道具は `town/data.js` の TOOLS と BUILDINGS(PRODUCTS の写し)なので、道具を足す・直すときは `town/data.js` と `index.html` の `<noscript>` の一覧も直す(`scripts/check-site.mjs` の6項が、名前・一行・行き先・誰向け・利用条件・建物ごとの数と顔ぶれ・JS なしの一覧・病院の中の札を PRODUCTS と照合する)。町の中の物(`town/interiors.js`)は任意で後から。用途を増やすには建物が要り、社長の判断。
- **活動** … `projects/index.html`の`ACTIVITIES`配列。同上。
- **記事** … `journal/index.html`は`notes/feed.json`(noteのRSSから自動生成)を読み込み、タイトル・本文からタグを自動付与。記事が増えても手作業ゼロ。タグは`TAGS`配列で追加。
- **物語** … `stories/index.html`の`STORIES`配列。
- **ナビ/フッター** … `shared/bridge.js`の`NAV`配列が唯一の情報源。ページ追加時はここに1行足せば全ページのヘッダー・ドロワー・フッターに反映される。トップ(町)は `window.BRIDGE` から同じ中身を描く(JS なし用に `index.html` に書いた同じ中身は check-site 6項が照合するので、NAV を変えたら `index.html` のヘッダー・メニュー・フッターも直す)。
- **将来のMega Menu化** … ページ数が15を超えたら、`NAV`にグループキーを足してヘッダーをグループ型に切り替える(構造は既にデータ駆動なので、描画関数の変更のみ)。
- **個別記事をサイト内に持つ場合** … `journal/posts/xxxx.html`を追加し、`feed.json`相当のローカルインデックス(`journal/index.json`)を併設する設計を推奨。

## 11. 写しの運用(プロダクト詳細ページ)

- LPが実物について述べる事実(画面名・項目名・色分け・数値・件数)は、同じページ上で照合できる形で示す。原則として、無加工の実物の写し1枚と、その撮影日を記す。
- 写しは体験の代替ではなく、照合の錨である。デモへの導線(憲法第28条の「触れる瞬間」)を写しで置き換えない。
- 写し自体はテーマに追従しない。枠・キャプション・余白は両テーマで等価に設計する(第22条後段)。
- 実物が変わったら写しを撮り直す。すぐ撮り直せないなら、古い撮影日のまま掲げる——日付が古さを自己申告する。
- 紹介 LP の冒頭の写し(`.lp-shot`)も同じ運用。alt は写っている画面をそのまま述べる(写っていない機能を alt で語らない。PM 2026-10-11)。1ページに写しは1枚(第22条)。
- トップ(町)の建物の中の実画面も写しで、同じく加工しない・写しの中の色を枠の外へ持ち出さない(憲法第22条 町の但し書き (4))。写しの「1ページ1枚」は第22条 v1.4 のとおりトップに適用しない(v3.4)。
