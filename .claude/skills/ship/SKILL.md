# 出荷手順

CLAUDE.mdの流れ（pm→制作→qa＋領分照合→pm総合判定→社長）の出荷部分を固定したもの。
憲法第34条（公開前照合の義務）と第9条4号（意志の強さを前提にしない）の実装である。
以下を順に実行する。段を飛ばさない。

## 1. 機械検査

```
node scripts/check-site.mjs
```

落ちたらここで終了。違反を直してから再実行する。直せない事情がある場合のみ
`scripts/check-site.allowlist.json` に理由付きで登録し、社長への報告に含める。

## 2. 領分の照合

`git status` と `git diff` で変更範囲を特定し、関与するエージェントを決める。

| 変更範囲 | 呼ぶエージェント |
|---|---|
| 公開ページの文言・記事 | `editor`（第17〜20条の照合） |
| 見た目・レイアウト・UX | `designer`（第21〜29条の照合） |
| ページ・機能の追加変更すべて | `qa`（技術検証。公開物に触れたら必ず） |
| 内部文書・scripts・.claude のみ | editor/designerは呼ばない。qaも変更が動くものなら実地検証のみ |

各エージェントには変更範囲を伝え、合否と根拠を受け取る。

## 3. PM総合判定

`pm` に1と2の結果を渡し、第34条チェックリストに照らした総合判定（出荷可否）を受け取る。
不合格なら差し戻し。修正後は1からやり直す。

## 4. 判定の記録

`cockpit-76a805/shiplog.jsonl` に1行追記する（1出荷=1行のJSONL）。スキーマ：

```json
{"date":"YYYY-MM-DD","commit":"","scope":"変更の一言要約","checks":{"machine":"pass|fail","qa":"pass|fail|n/a","editor":"pass|fail|n/a","designer":"pass|fail|n/a"},"verdict":"shipped|held","notes":"違反・allowlist登録・保留事項。なければ空文字"}
```

- `commit` の空文字は「この行を含むコミット自身」を指す（記録は出荷と同じコミットに入れるため、自身のハッシュは書けない）。過去の出荷を指す場合のみ短縮ハッシュを書く
- 関与しなかった領分は `"n/a"`
- `verdict: "held"`（保留）の場合も記録する。保留の理由をnotesに書く

## 5. 台帳更新とコミット

```
node scripts/update-ledger.mjs
git add <変更ファイル> && git commit
```

公開（masterへのマージ・デプロイ）の最終判断は常に社長にある。

## 6. 社長に見せるものを渡す

出荷報告には、**社長がその場で見られる実物**を必ず添える。「見てください」だけで終わらせない。
2026-07-25の社長指示（「見てくださいっていう割にURLが無い。出したタイミングで見せるものを出せ。徹底して」）による恒久ルール。

- ページ・見た目の変更 → **Artifactとして発行し、URLを渡す**（第一の手段。ファイル送付は環境により開けないことがあった）。単体で動かないページは主要画面のスクリーンショット（ライト/ダーク・モバイルなど判断に必要な状態を選ぶ）。あわせてマージ後の本番URL（https://bridge-med.github.io/bridge-lp/...）を明記する
- 内部文書のみの変更 → 差分の要点を本文に書く（ファイル送付は不要）

これを済ませるまで、出荷報告は完了ではない。
