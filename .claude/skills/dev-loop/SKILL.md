# 開発ループ

CLAUDE.mdの流れ（pm→制作→qa＋領分照合→pm総合判定→社長）の**制作部分**を固定したもの。
docs/context.md 9章（実装時の判断基準）と15章（仕事の進め方の実践ルール）の実装である。
着手から出荷判定の手前までを扱う。コミット・記録は `ship` スキルの領分であり、ここでは重複させない。

原則：段は飛ばさないが、太らせない。各段の成果物は数行でよい。
長い計画書・網羅的なチェック表・過剰な報告は、それ自体がcontext.mdの禁じる「AIが作った感」である。

## 0. 種別の判定

依頼を次のいずれかに分類し、対応する調整でループを回す。迷ったら feature として扱う。

| 種別 | 目安 | ループの調整 |
|---|---|---|
| feature | 新しい機能・ページ・部品 | 全段を実行。スコープや優先順位に迷いがあれば着手前に `pm` |
| bugfix | 壊れているものを直す | 1で再現条件を確定してから直す。8は軽く（思想より再発防止）。原因と再発条件を学びとして残す |
| ui-improvement | 見た目・導線の改善 | 着手前に `designer` へ方針を相談。6でモバイル・ライト/ダークを実物で確認 |
| refactor | 挙動を変えない整理 | 8は省略可。5で「挙動が変わっていないこと」を差分から確認する |
| product-idea | 新プロダクト・大きな機能の構想 | 1〜3のみ。実装せず、context.md 13章の形式（現状の問題→変更内容→影響→注意点）で提案を返し、社長の判断を待つ。第14条（空室の禁止）と第31条（道具の義務）に照らす |

## 1. 理解 — Task Intake

- 依頼の目的・影響範囲・既存機能との関係を、既存コードと前後関係から把握する。過剰な確認で開発を止めない（context.md 8項）。
- 依頼がcontext.md 9章の判断基準（入力を増やしすぎない・既存で代替できないか・AI自体が目的になっていないか等）に反する疑いがあれば、そのまま実装せず、問題点と代替案を提示する。

## 2. 調査 — Repository Inspection

- 対象ページ・コードの実物を開く。憶測でパスや仕様を語らない。
- 類似の既存実装を探し、パターンを踏襲する。新しい部品を発明する前に `shared/bridge.css` / `shared/bridge.js` のトークン・部品で表現できないかを先に考える。
- データの唯一の情報源を確認する：ナビは NAV 配列、プロダクトは PRODUCTS 配列、活動は ACTIVITIES 配列。

## 3. 計画 — Implementation Plan

- 変更対象ファイル・実装方針・リスクを数行で整理する。完成の定義を1〜3行で確定させる。
- 1コミットで出荷できる単位を超えるなら、`pm` に分解を相談する。

## 4. 実装 — Implementation

- 既存設計を優先し、最小限の変更で実装する。理由なき大規模な書き換えをしない。
- 技術メモ（CLAUDE.md）の禁則を守る：色のハードコード禁止、ナビはNAV配列経由、見出しに句点を付けない、「!」を使わない。
- スマートフォン表示を最優先に作る（context.md 7章）。

## 5. 自己レビュー — Self Review

`git diff` を通しで読み直し、次を確認する。

- 意図しない変更・消し忘れ・仮文言・ダミーデータが残っていないか
- 依頼された箇所だけの機械的な変更になっていないか（関連する画面・導線への影響）
- 既存ページとの統一感があるか。同じ役割の重複を作っていないか

## 6. 検査 — Quality Check

- `node scripts/check-site.mjs` を走らせる（このリポジトリの機械検査はこれが全て。lint/typecheck/testは無い。ビルドも無い）。
- 機械が見られないものは実物で確認する：変更ページを開く、モバイル幅（≤920px）、ライト/ダーク両テーマ。
- PWA（sw.jsを持つプロダクト）に触れたら `CACHE` の版名を上げる。

## 7. 修正ループ — Repair Loop

- 検査で問題が出たら、原因を特定してから直し、6へ戻る。対症療法で潰さない。
- 同じ箇所で3回失敗したら手を止め、3の方針から見直す。

## 8. プロダクト照合 — Product Review

出荷判定に出す前に、作った本人として自問する（context.md 9章・6章の要約）。

- 利用者・読者にとって実際に役立つ変化か。入力や操作を増やしていないか
- AIを使うこと自体が目的になっていないか。AIを前面に出しすぎていないか
- 既存の機能・ページと重複していないか
- 画面が複雑になっていないか。説明を詰め込みすぎていないか
- BRIDGEの思想（CONSTITUTION.md・docs/context.md）と一致しているか

1つでも自信を持って答えられない項目があれば、まず削ることを検討し、判断に迷えば `pm` に相談する。

## 9. 出荷 — Completion

- ここから先は `ship` スキルに従う（機械検査→領分照合→PM総合判定→shiplog記録→台帳更新→コミット→実物を渡す）。
- 完了報告はcontext.md 15章の形式で簡潔に：何を変えたか／なぜ／体験がどう変わるか／確認したこと／残課題。変更行数や技術説明だけで終わらせない。
- 再利用できる学び（ハマった原因、次も使えるパターン、bugfixの再発条件）があれば、shiplogの `notes` に1行で残す。学びの台帳を別ファイルに増やさない。
