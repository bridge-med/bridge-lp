# BRIDGEの文章を作る

`dev-loop` の制作で使う。公開前の照合と記録は `ship` に集約する。以下のパスはリポジトリルート基準。

## 媒体と根拠を確認する

1. `CLAUDE.md` と `CONSTITUTION.md` 第4〜5章、対象の文章と前後の画面を読む。
2. `docs/context.md` 冒頭・§6〜§8を読む。noteなら末尾の「付記: noteでの発信」も読む。
3. 公開サイトのコピー、プロダクトのUI文言、note、ゲームの案内文・人物の発話を区別する。文体と一人称は一次文書の棲み分けに従い、すべてを同じ語り口へ揃えない。
4. 読む人と、増やす選択肢を一文で定める。BRIDGE全体の対象とCompass固有の対象を混同しない。
5. 実績・体験・数値の根拠を確認する。本人が話していない実話、未計測の効能、他者の物語を作らない。足りない事実は削るか確認が必要な箇所として残す。

## 書いて削る

- 利用者がすぐ分かる言葉にする。抽象語を増やすより、確認できた場面や行動を一つ選ぶ。
- 重複する説明と修飾を削る。文字が多い場合は優先順位や置き場所も見直し、カードの追加で解決しない。
- 静かで誠実な声を守る。実績を盛らず、前向きさや成長を強要しない。AIを主役にした約束を足さない。
- 憲法第19条の禁則を対象媒体の適用範囲で確認する。ゲームの例外はcontext冒頭の発効文に照らす。制度の正式名称は、短くするためだけに変えない。
- Compassなら `bridge-compass` と既存テストも参照し、適職・適性を断定する表現へ変えない。

## 照合して渡す

- 原文と修正文を比較し、意味の変化、対象者の勝手な拡大、根拠のない断定がないか確認する。
- 公開文は `editor` へ媒体・根拠・変更箇所を渡して照合を受ける。noteの発信計画は既存の `pr` の領分へ渡す。
- 言い回しの変更でレイアウトが変われば `bridge-design` の実物確認も行う。
- ファイルを変えたら `node scripts/check-site.mjs` と関連テストを実行する。何を削り、何が伝わりやすくなったかを簡潔に報告する。
