# Compassを変更する

`dev-loop` に固有の調査と検証を加える。UIは `bridge-design`、文言は `bridge-copy` を併用し、出荷は `ship` に集約する。以下のパスはリポジトリルート基準。

## 現在の仕様を読む

- `CONSTITUTION.md` 第30条のCompassの但し書きと第31条、`compass/index.html` の対象・自己申告を読む。名称の例外を他の道具に拡張しない。
- `compass/app/data.js` で質問・資産・役割・橋・言いかえの定義を確認する。
- `compass/app/engine.js` で判定と説明の流れを確認する。純関数とDOMを分離する。
- `compass/app/app.js` / `styles.css` で操作、表示、保存・共有の実装を確認する。
- `compass/tests/engine.test.mjs` のpersonaと性質のテストを読む。以下は現在の境界の索引であり、実際の挙動はコードとテストで確かめる。

## 判定の境界を守る

- 回答→経験資産→役割→橋の流れと、本人の回答に基づく理由を維持する。適職・適性の断定や画面への点数・%表示を加えない。
- 結果の橋は経験・関心・未発見の3枠、重複なし。関心だけやQ7だけで結果を決めない。重みを調整する場合は目的と変化をpersonaの前後比較で示す。
- Q5は「できるが、やりたくない」。経験資産を減点せず、役割との関わり方として扱う。Q4との重なりを入力エラーにしない。
- 職種は言いかえの選択に使い、橋の選定を変えない。対象や職種を変更する場合は既存の対象を確認し、変更をPMへ提示する。
- Q9/Q10は本人の記述として扱い、判定にも共有文にも入れない。表示を変える際は安全なテキスト表示を維持する。
- Q6/Q8で選んだ関心が3つの橋に入らない場合、`openInterests` で「気になっている方向」を残す。AIを選んだら必ずDXの橋を入れる仕様へ、依頼の意図を確認せず変えない。
- 経験資産のタグ・名前と橋の名前を同じ言葉にしない。リンク先と役割・資産の参照整合を保つ。

## 検証する

1. 修正依頼なら回答を特定して再現する。判定変更前に橋・理由・tags・openInterestsを取得し、変更後と比較する。
2. `node --test compass/tests/*.test.mjs` と `node scripts/check-site.mjs` を実行する。意図して結果を変えた場合も、既存の不変条件を壊していないか確認する。失敗を消すだけの期待値変更はしない。
3. ロジックを変更した場合は、実際の不具合や要望の回答を回帰テストへ加える。文言だけの変更では不要なテストを増やさない。
4. UIを変更した場合は開始→回答→戻る→結果→共有までを実物で確認する。Q4/Q5の重なり、自由記述、橋に入らない関心の表示も確認する。
5. 判定と表示の変更を分けて説明し、確認結果と未確認の操作を `ship` へ渡す。
