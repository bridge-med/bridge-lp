# BRIDGEのUIを作る

`dev-loop` の調査・計画・実装・検査で使う。出荷判定と記録は `ship` に集約する。以下のパスはリポジトリルート基準。

## 参照を揃える

1. `CLAUDE.md` の一次文書の優先関係と対象プロダクトの例外を確認する。
2. `CONSTITUTION.md` 第6〜7章と、`docs/context.md` 冒頭・§7を読む。
3. `docs/design-system.md` §0〜§6、`docs/ia.md` の対象ページの役割を読む。
4. 対象ページと、読み込まれるCSS/JSの実体を開く。ブランドサイトなら `shared/bridge.css` / `shared/bridge.js` の既存部品・トークンを調べる。
5. clinic-flow-3dなら独自のデザイン系と `clinic-flow-3d/docs/ux-audit-v85.md` §4を参照する。ブランドの色・書体を強制しない。他のアプリへ例外を広げない。

## 方針を決めて実装する

- 「AIっぽい」を装飾だけの問題にしない。主役、説明の重複、均質なカード、抽象的なコピーを確認し、まず情報の削除・順序・導線を見直す。
- 使える既存の部品・型・トークンと変更ファイルを挙げ、`designer` に方針を相談してから実装する。新しい共通部品の追加可否は design-system §6で判断させる。
- 色・書体・モーションの値は実体を参照する。過去のチャットや他社の見た目をBRIDGEの規範として持ち込まない。
- トップとProductsのガラス・太いゴシックの例外は憲法の但し書きの範囲で使う。他ページへ広げず、トップの例外を誤って全面禁止にもしない。
- 動きには構図・主役・現在地が変わる目的を付ける。操作を妨げず、`prefers-reduced-motion` とJSなしで内容を読める状態を用意する。

## 実物を確認する

- 変更ページをモバイルとPC、ライトとダークで確認する。対象の実装にないテーマを新たに作る場合はスコープ判断を先に行う。
- はみ出し、主要帯の高さ、見出しの折返し、タップ領域、フォーカス、次の行き先を確認する。該当する44px/AA基準も照合する。
- 数値は現場が計測し、状態・viewport・画像とともに `designer` へ渡す。取得できないものは未確認と明記し、合格を推測しない。
- `node scripts/check-site.mjs` と対象固有の検証を実行し、結果を `ship` へ渡す。完了報告では変わった体験と実物を示す。
