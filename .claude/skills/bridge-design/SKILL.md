# BRIDGEのUIを作る

`dev-loop` の調査・計画・実装・検査で使う。出荷判定と記録は `ship` に集約する。以下のパスはリポジトリルート基準。

## 面を決めて参照を揃える

1. 対象がブランドの面かプロダクトの画面かを `docs/design-system.md` §0 で決める。思想は共有し、デザインはプロダクトごとに選ぶ(`CONSTITUTION.md` 第30条の2)。
2. ブランドの面なら、`CONSTITUTION.md` 第6〜7章、`docs/design-system.md` §0〜§6、`docs/ia.md` の対象ページの役割を読み、`shared/bridge.css` / `shared/bridge.js` の既存部品・トークンを調べる。
3. プロダクトの画面なら、`docs/design-system.md` §5(前提・共通の品質基準)、`docs/context.md` 冒頭(§7 の読み方)、そのプロダクトのトークン・部品と前提の記録(自身の styles.css・README。clinic-flow-3d なら `clinic-flow-3d/docs/ux-audit-v85.md` §4)を読む。ブランドの部品・色・書体を初期値にしない。
4. 新しいプロダクトと、デザインの方向の作り直し(系の入れ替え)なら、前提(誰が・何を・どこで・どんな体験)を先に決め、デザインの方向を2〜3並べて `designer` に比べてもらう(§5)。既存のデザインの再利用から始めない。

## 方針を決めて実装する

- 「AIっぽい」を装飾だけの問題にしない。主役、説明の重複、均質なカード、抽象的なコピーを確認し、まず情報の削除・順序・導線を見直す。
- 使える既存の部品・型・トークン(その面のもの)と変更ファイルを挙げ、`designer` に方針を相談してから実装する。ブランドの面の新しい共通部品の追加可否は design-system §6で判断させる。
- 色・書体・モーションの値は、その面の実体(トークン)を参照する。過去のチャットや他社の見た目をブランドの面の規範として持ち込まない。プロダクトで他の製品の型を参考にするときは、前提に合う理由を添える。
- (ブランドの面)トップとProductsのガラス・太いゴシックの例外は憲法の但し書きの範囲で使う。他ページへ広げず、トップの例外を誤って全面禁止にもしない。
- 動きには目的を付ける(ブランドの面では構図・主役・現在地が変わること)。操作を妨げず、`prefers-reduced-motion` で止まる状態を用意する。演出で隠した中身を、隠れたまま残さない。ブランドの面はJSなしでも内容を読めるようにする。

## 実物を確認する

- 変更ページをモバイルとPC、その面が持つテーマすべてで確認する。対象の実装にないテーマを新たに作る場合はスコープ判断を先に行う。
- はみ出し、主要帯の高さ、見出しの折返し、タップ領域、フォーカス、次の行き先を確認する。共通の品質基準(§5。44px/AA など)も照合する。
- 数値は現場が計測し、状態・viewport・画像とともに `designer` へ渡す。取得できないものは未確認と明記し、合格を推測しない。
- `node scripts/check-site.mjs` と対象固有の検証を実行し、結果を `ship` へ渡す。完了報告では変わった体験と実物を示す。
